# Real-world qualification results — 2026-09-07

Result: **195 distinct automated cases passed, zero failures in completed final
runs**: 171 default Rust cases, 12 extension JavaScript cases, five fixture
contract cases and seven explicitly enabled real-browser/CLI/public-page cases.
This is a scoped alpha qualification record, not a production-safety certification.
The installed-extension/native-human/keychain acceptance gate is **NOT RUN**.
New-process and HTTP effects are **NOT IMPLEMENTED**.

## Source, environment and scope

- MagicVault `0.3.0` working tree tested before commit, based on
  `baba4b1b68fa4f2771a5436175360664fc7a2470`, including the qualification additions.
  No commit, push, published tag or CI run is attested by this record.
- macOS 26.6 (25G72), arm64; Rust/Cargo 1.92.0; Node.js 22.19.0;
  Google Chrome 152.0.7977.82. These results do not qualify every claimed minimum
  compiler/browser version, Chromium brand or operating system.
- Locked offline Cargo builds with a warm external temporary artifact cache.
  The test-support dependency declaration was updated with already-locked
  dependencies; lockfile synchronization selected zero new package versions.
- Browser-delivery changes in this test run touch MagicVault only. Shared `magicvault-core`
  `0.1.3` and `magicvault-primitives` `0.1.1` source remain unchanged. The sibling
  MagicRun working tree was clean; no MagicRun or Magician changes were made.
- CLI/browser qualification uses the actual CLI executable, service broker,
  Unix IPC, encrypted custody path and CDP adapter. Only human interaction and
  custody-key storage are test-only providers. It does not launch a production
  daemon with bypassed consent or exercise the real macOS keychain/dialogs.

## Case observations

- **B-01/B-02:** Both headed and modern-headless Chrome accepted the exact
  username/password fields, delivered input/change events, and left submission
  to the original browser tool. A second independent CDP peer remained usable
  after MagicVault disconnected. Own operation outcomes contained no canary.
- **B-03:** Readonly, disabled-fieldset, hidden, file, too-short, ambiguous,
  missing and shadow-boundary locators refused before the first write. An input
  handler replacing a later field produced partial delivery; the replacement
  stayed empty.
- **B-04/B-05:** A stale document could not fill the replacement page. Explicit
  same-origin iframe delivery worked without filling the top page; an opaque
  sandboxed frame was omitted from discovery.
- **C-01:** Actual CLI pairing, enrollment, permission configuration, registration,
  discovery, fill, status and disconnect completed through real local IPC and
  Chrome. A denied fill left the destination empty. CLI stdout/stderr and typed
  audit checks did not disclose the synthetic value.
- **Public smoke:** Visited [Example Domain](https://example.com/) and filled
  [Selenium's demonstration form](https://www.selenium.dev/selenium/web/web-form.html)
  with the fixed public canary, through the real CDP adapter. No form submission,
  login, real credential, persistent personal profile or TLS bypass was used.
  This is compatibility evidence, not provider certification or endorsement.
- **Fixture contracts:** Actual Node children exercised synthetic environment
  and stdin delivery, same-process explicit IPC rotation, refusal of invalid or
  oversized input, and a deliberately echoing fixed public canary. These qualify
  future test destinations, **not** a working `secure_new_process` or stateful
  MagicVault service integration.
- **Interactive inspection:** Playwright inspected the synthetic login and
  frame pages in a separate isolated headed Chrome session. This checked that
  the reusable runbook pages expose usable fields/labels and frame cases; it
  did not install the extension or qualify native messaging.
